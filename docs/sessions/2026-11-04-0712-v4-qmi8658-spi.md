# 2026-11-04: v4 QMI8658 over SPI (W4b, class S)

- **Finding**: the T-Beam Supreme's QMI8658 is on SPI, not I2C. Stock `variants/esp32s3/tbeam-s3-core/pins_arduino.h:30-37` puts it on the SD card bus (SCK 36, MISO 37, MOSI 35, SD CS 47) with `IMU_CS` 34, and LilyGo's `QMI8658_GetDataExample.ino:53-56` starts it with `qmi.begin(SDCardSPI, IMU_CS)`. The old `init()` probed I2C 0x6B and could not find it. Stock Meshtastic has no QMI8658 driver; its bus scan names any device at 0x6B a QMI8658 without reading the chip ID (`src/detect/ScanI2CTwoWire.cpp:556-576`).
- **Bus sharing**: the SD card uses `SPIClass SPI_HSPI(HSPI)` (`src/FSCommon.cpp:20-22`), started in `setupSDCard()` under `spiLock` (`:385-386`). LoRa uses the default `SPI` (FSPI) on pins 12/13/11 (`src/main.cpp:836-844`); `src/main.cpp:164` (`SPI1(HSPI)`) is only built with `HW_SPI1_DEVICE`, which tbeam-s3-core does not set. The IMU therefore reuses `SPI_HSPI` (same instance, no second owner of HSPI) and takes `spiLock` for init and every read.
- **SensorLib 0.3.4**: `begin(SPIClass &spi, uint8_t csPin, int mosi = -1, int miso = -1, int sck = -1)` exists (`SensorQMI8658.hpp:271`). With no pins it does not call `spi.begin()` and only drives CS around each transfer inside `beginTransaction`/`endTransaction` (`platform/arduino/SensorCommArduino_SPI.hpp:62-86, 114-121`).
- **Not done**: no build and no `pio test`. The environment's proxy refuses `api.registry.platformio.org`, so the espressif32 platform, toolchain and library packages cannot be installed. The commit carries no `Checksum` trailer: the sealing hook and key are not in this container. Hardware gate pending.
